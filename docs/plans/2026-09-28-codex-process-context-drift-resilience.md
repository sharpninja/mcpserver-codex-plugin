This document is a plan and TODO companion only. It does not create capsules, change implementation code, or approve implementation.

## Architecture: process data in MCP, generic enforcement in the plugin

### Active process manifest and exact policy

MCP must provide an authoritative active-process binding for the current workspace, TODO, and slice. It resolves to a versioned, approved process manifest. The manifest declares methodology ID/version, phase graph, transitions, predecessor gate IDs, evidence contracts/validator IDs, guarded operation classes, canonical capsule IDs, capsule-to-phase references, source revisions/digests, and rules for completion. The plugin has no BDPv4-specific phase names, IDs, transition order, or mock gate in executable code. A new approved process or BDP revision updates MCP data and validators, not the plugin. Safe behavior when no process is assigned must be explicit in the manifest/API and migration policy; do not infer ungoverned status from a failed fetch.

Process Capsules are exact canonical text records selected by the active MCP manifest. Fetch the manifest-pinned memory ID and approved revision through workflow.memory.get or equivalent exact lookup. A confirmed missing memory record may use the manifest-declared, commit-pinned canonical GitHub source URL only after validating the repository/path/ref, expected source digest, and approved source mapping; a transient MCP outage or missing manifest does not silently become a GitHub fallback. Reject missing, duplicate, wrong-scope/type, wrong-version, mismatched, or unverified-source records. Semantic recall, title matching, summarization, and paraphrase cannot satisfy an ID. BDPv4 capsule IDs and GitHub URLs live only in MCP manifest data and test fixtures, never plugin code or memory-descriptor.json.

Keep memory-descriptor.json backward compatible for ordinary memories. Add only generic discovery/schema settings there, or use a dedicated generic process descriptor; no canonical prose, BDP phase map, or pinned BDP IDs in the plugin. The exact active manifest and IDs come from MCP. Hash exact canonical UTF-8 content bytes under a versioned byte/line-ending contract. The current memory_get response exposes version and McpServer MemoryClient.ListVersionsAsync exposes stored content snapshots; the new active-process API must atomically pin an approved snapshot version and SHA-256 digest rather than assuming those existing reads alone form an approval contract.

### Generic process context, cache, and lease

Add lib/process-context.ps1 to fetch and validate the active manifest/capsules, resolve current phase, manage verified cache and leases, rehydrate context, emit heartbeat, and return structured blocks. Keep lib/memory-context.ps1 dedicated to ordinary memory. Reuse Resolve-McpCacheDir for workspace/session isolation.

The MCP active-process manifest and execution state remain authoritative. A scoped last-known-good cache is a receipt/read fallback: store manifest/capsules, exact IDs, approved source revisions, per-source and aggregate SHA-256 digests, descriptor/schema version, workspace binding, and fetch time atomically. A manifest-approved canonical GitHub source may supply exact policy text when its MCP memory record is confirmed missing; a total MCP outage cannot authorize transitions. During outage, use only an unexpired, digest-verified cache compatible with the last trusted binding for context rehydration. A local hash detects corruption but does not authenticate against hostile cache replacement; if hostile tampering is in scope, require a backend-signed receipt verified with a pinned public key. No secrets in policy, cache, or logs. Offline cache never authorizes an MCP transition or accepted completion.

The scoped policy/process lease must include methodology/version, workspace/TODO/slice, active phase and gate revision, turn/request identity, capsule IDs, source revisions, per-capsule/aggregate SHA-256, MCP source status, context/process epoch, injection timestamp, expiry, and authoritative state revision. Invalidate on manifest/policy/phase/workspace/session/epoch change. Use server compare-and-swap or equivalent revision checks for concurrent and background turns and idempotent request IDs for retry. A missing or invalid critical lease yields PROCESS_CONTEXT_UNAVAILABLE or PROCESS_POLICY_STALE at guarded boundaries. Ordinary memory remains fail-soft.

Rehydrate at session/bootstrap, each user-prompt boundary, supported post-compaction, phase transition, requirements mutation, implementation entry, validation entry, completion/done, hostile-validation launch, and every other guarded MCP mutation. Pre-compaction may flush receipts; compaction detection is an optimization, not a correctness requirement. Emit a small process heartbeat (methodology, phase, digest, epoch) on healthy guarded calls. Emit full exact capsules when a lease is absent/stale, phase or digest changes, post-compaction occurs, or a forbidden transition is attempted.

### Generic state and proof-carrying gates

Persist the current process state and gate evidence in MCP, keyed to workspace, TODO, slice generation, active manifest revision, and state revision. The plugin evaluates declared predecessor relationships and evidence contracts generically; process-specific validators execute through an approved MCP validator registry or server endpoint. No plugin branch should say If BDPv4 or If mock validation. Existing TODO statuses remain the outer lifecycle; the active manifest describes how its inner gates map to those statuses. Do not assume TestReady itself proves any process-specific gate.

Evidence needs command, runner/environment, exit code, exact test or validation selection, start/end time, output/artifact hash, relevant file/diff fingerprints, actor, session turn, source revision, declared gate/validator ID, and expected/observed result. A plain text claim is insufficient. The active process specifies which receipts are required and how test intent/quality is reviewed. For the BDPv4 acceptance scenario, the manifest requires requirements/AC ready, tests written, tests mock-validated, real implementation allowed, same tests real-green without behavior-providing mocks, full current-plus-prior suite green, required hostile validation, and done. Expected real-red is recorded where the active BDP process requires it. Assertions accepting unrelated exceptions, unobserved command failure, or ineffective freshness checks cannot count as valid proof.

A blocked transition returns PROCESS_GATE_BLOCKED with authoritative process state, missing predecessor/evidence, exact relevant canonical policy excerpt, and remediation. A production edit observed before the active process's mock-validation gate makes that BDP slice noncompliant until explicit remediation/restart. The generic engine detects early edits by comparing process-defined protected path classes, recorded pre-gate baseline/diff, and edit receipts at guarded boundaries. It does not claim to intercept every local edit.

### Host limitation and hard enforcement boundary

Plugin preflight belongs in Invoke-ReplMethod/Invoke-ReplRawCore for manifest-classified guarded workflow.todo, requirements, validation, hostile-review, session-completion, and related mutations. Keep safe reads, recovery, and evidence submission available under explicit generic method classes. Add current-process checks to Start-PluginSession, Open-PluginTurn, post-compact, and Close-PluginTurnIfNeeded. lib/stop-gate.ps1 must expose structured blocks and must not auto-accept governed work without a valid lease/evidence.

A direct native MCP client can bypass plugin wrappers, and unrelated tools can edit local files. To meet the requested hard contract, McpServer must enforce active-process lease, epoch, state, and predecessor evidence at the authoritative mutation, accepted-completion, and done endpoints. The plugin cannot alone guarantee those outcomes. Guard local edit workflows where the host permits, otherwise detect later and block acceptance. If server-side enforcement is absent, do not declare the feature complete or claim stronger prevention.

## Acceptance criteria

1. MCP selects the active approved development process for a workspace/TODO. A new version or different process changes policy/gates without editing or redeploying plugin code.
2. Exact approved capsule IDs/text/revisions/digests and authoritative phase reconstruct after conversational context loss. Plugin configuration contains generic discovery/schema only; no BDPv4 IDs, phase names, gate order, or prose.
3. Ordinary memory/legacy descriptors remain fail-soft and compatible. On confirmed process-memory not-found, an active MCP manifest may authorize a pinned canonical GitHub source whose exact bytes, ref, and digest verify; that source can support a current lease while MCP process state is live. If the manifest, GitHub source, or verification is unavailable, critical context fails closed. Verified offline cache may rehydrate context but cannot authorize acceptance while MCP is down.
4. A current lease binds methodology, phase, workspace, slice, turn/request, revisions/digests, timestamp, and epoch. Stale, replayed, concurrent-conflicting, cross-workspace, and wrong-process leases fail.
5. All named deterministic boundaries restore process context without a required compaction signal. Full capsule appears when needed; healthy heartbeat is compact.
6. Authoritative McpServer guarded mutations/completion/done reject phase jumps and missing predecessor proof under the active process. BDPv4 fixture specifically rejects production entry before mock validation, missing real-green/full-suite/hostile proof, and early production edits without remediation.
7. Blocks include structured code, current process state, missing gate/evidence, exact canonical excerpt, and recovery guidance; session-log receipts preserve why.
8. Every named failure mode has meaningful tests. Each implementation increment follows mock-validation-before-real-code under current BDPv4, then real-green/full-suite/hostile gates.
9. Warm heartbeat target: at most one full capsule per unchanged phase/epoch. Measure p95 plugin-local processing separately from end-to-end guard latency (including MCP round trips) and full-capsule rehydration latency/bytes/tokens; the provisional under-250-ms target applies only to warm local plugin work, excluding network and full capsule transfer. Set end-to-end and rehydration limits from an observed baseline before canary rollout. No secrets in memory, cache, or logs.
10. Existing ordinary-memory users and ungoverned TODOs migrate safely. A fetch failure never silently changes governed work to ungoverned or done.

### B. Authoritative contracts and API

These choices resolve the earlier "Remaining approval checks" for review. They become binding only after approval of this whole document and coordinated McpServer work. The approved process is a server-owned data object; the plugin contains a generic interpreter and client adapter, never a BDPv4 branch.

#### B1. Persisted records and identities

ProcessManifestSnapshot is immutable and stores manifestId, semantic version, schemaVersion, raw UTF-8 manifest bytes, SHA-256, methodologyId/version, policyRefs, phase graph, predecessor gate IDs, evidence schema and validator IDs, guarded operation classes, protected path classes, outer TODO-status mapping, completion conditions, and optional fallback sources. PolicyRefs contain exact memory ID, scope, immutable content version, content digest, phase IDs, and digest-checked excerpt offsets or unique anchors. The server rejects unknown schema or validator IDs on activation; it does not interpret unknown rules as optional.

ProcessBinding stores bindingId, scope kind (global/workspace/TODO), scope ID, manifest snapshot digest, assignment state (Assigned or ExplicitlyUnmanaged), binding revision, epoch, actor, signed approval receipt, and effective time. Binding lookup precedence is explicit TODO, then workspace, then approved global default. A slice pins bindingId/revision when created. A changed manifest or binding cannot silently replace an active slice; migration verifies historical gates or starts a new generation. No binding, ambiguous binding, or failed fetch means Unavailable.

ProcessState stores workspaceId, todoId, sliceId, generation, bindingId/revision, manifest digest, phaseId, stateRevision, contextEpoch, approved plan snapshot digest when the manifest requires a plan, gate results, and evidence IDs. Use a database-backed authoritative row and immutable event history. Existing TODO execution statuses (Draft, Planned, TestDesign, TestReady, Implementing, Validating, Blocked, Complete, Cancelled) remain the outer lifecycle and are mapped by the manifest. The current TodoExecutionService JSON state is a legacy view or projection, not the sole source of governed gate truth. TestReady by itself does not prove mock validation.

ProcessLease is an opaque, random server-side ID with issuedAt/expiresAt (five minutes), actor, workspace/TODO/slice/generation, sessionId, turnRequestId, binding epoch, phase, state revision, manifest/policy digests, approved plan digest when required, source status, and last injection time. Every guarded request supplies leaseId, expectedStateRevision, and idempotencyKey. Server checks the live binding and state, not only fields echoed by the client. On phase, policy, binding, workspace, session, or epoch change, the old lease fails. Repeat of an identical idempotency key returns the stored result; a different payload with the same key blocks.

PlanSnapshot stores snapshotId, workspaceId, todoId, workspace-relative path, exact raw bytes (BLOB), byte count, SHA-256, importedAt, importer, preceding snapshot ID, and approval receipt/status. Store bytes, not only a string: McpDbContext.SanitizeStrings changes Unicode dash code points in string properties. An approved snapshot never changes in place. The mutable working file is a candidate source only; the signed snapshot is the approved plan.

EvidenceReceipt stores receiptId, gateId, schema/validator IDs, actor and runner/reviewer identity, session/turn, command and working directory, exact test selection, mock/real mode, exit code, start/end time, parsed totals, output and artifact hashes, source/test/protected-path fingerprints, run generation, expected/observed result, and immutable source receipt reference. A trusted runner or separately authenticated reviewer produces the receipt. Arbitrary agent text can be attached as commentary but cannot establish a machine or independent-review gate.

#### B2. MCP operations and response contract

Add generic operations through the supported MCP client and workflow namespace:
- workflow.process.resolve(workspace, todoId?, sliceId?) -> assignment state, binding/manifest IDs and digests, phase, stateRevision, epoch, policyRefs, plan requirement, and source status in one consistent response.
- workflow.process.getPolicy(bindingId, policyRefId) -> exact pinned policy bytes or a typed ConfirmedNotFound; transport/auth/server failure has a different status.
- workflow.process.acquireLease(bindingId, sliceId, sessionId, turnRequestId, observedEpoch) -> opaque lease plus current state, or structured block.
- workflow.process.recordEvidence(leaseId, gateId, trustedReceiptId, idempotencyKey) -> immutable evidence ID after source and schema verification.
- workflow.process.transition(leaseId, expectedStateRevision, targetPhaseId, evidenceIds, idempotencyKey) -> new authoritative phase/revision/epoch and receipt, or structured block.
- workflow.plan.import(todoId, workspaceRelativePath, base64RawBytes, clientSha256) -> immutable snapshot ID, server-computed SHA-256 and byte count. Upload may be chunked under one import ID for transport limits, with final whole-byte hash verification.
- workflow.plan.getSnapshot(snapshotId) -> full exact bytes and provenance for review and readback.

Browser-only approval endpoints issue and verify WebAuthn challenges for manifest activation, binding assignment/migration, explicit-unmanaged classification, and plan snapshot approval. No ordinary workspace API key can enroll an operator credential or complete approval. A challenge contains action, workspace, target ID, target digest, expected revision, nonce, issuedAt, and five-minute expiry. Require user presence and verification, trusted credential, expected origin and relying-party ID, valid signature, unused nonce, and matching current revision. The first credential is enrolled by an operator-controlled administrative action outside the agent-accessible MCP API. Use a reviewed, pinned Fido2 .NET library version for verification; existing server-held transaction signing keys do not establish operator approval.

Every guarded operation has a typed response. PROCESS_CONTEXT_UNAVAILABLE means no live authoritative binding/state. PROCESS_POLICY_STALE means exact policy or digest/revision validation failed. PLAN_SNAPSHOT_MISMATCH means approved plan bytes or approval revision differ. PROCESS_GATE_BLOCKED means a predecessor, validator, or receipt is missing or failed. Include bindingId, current phase/stateRevision/epoch, missingGateIds/evidenceIds, an exact digest-checked canonical policy excerpt, and a specific remediation action. Do not emit full policy text on every healthy call.

#### B5. Proof-carrying gates and service-level enforcement

The active manifest declares phases, allowed edges, predecessor gate IDs, evidence schemas, validator IDs, and which operations require which phase. The generic engine evaluates the declared graph. Process-specific validators live in a reviewed server registry and are referenced by ID; the plugin dispatches generic references. Unknown validator IDs block activation, not silently pass. The first BDPv4 manifest declares requirements/AC ready -> tests written -> mock validated -> real implementation allowed -> real green -> full current-plus-prior suite green -> hostile validation -> done, with applicable real-red evidence. Another manifest uses a different graph to prove methodology independence.

A command runner on the workspace host issues immutable run receipts. It records runner identity; command ID/text and working directory; exact test selection/IDs; environment and mock/real mode; positive instrumentation that test doubles were exercised in mock mode; instrumentation that behavior-providing doubles are absent in real mode; exit code; start/end time; parsed pass/fail/skip counts; source/test/protected-file fingerprints; output and artifact hashes; and session/turn identity. The server validates runner identity and receipt integrity before attaching a receipt to a gate. An agent-authored "tests passed" statement is commentary only. Where runner instrumentation is unavailable, the gate stays incomplete.

For mock validation, the BDPv4 validator checks named behavior tests, exit 0, exercised doubles, assertions tied to current AC, and a pre-gate production baseline. For real-green it requires the same named tests and relevant assertion fingerprint, real production binding, doubles disabled/absent, exit 0, and matching source revision. Required real-red and cumulative full-suite receipts have their own run IDs and expected/observed exits. Command-failure proof contains independent missing, malformed, and nonzero cases for every required command; a later success cannot hide an earlier failure. Freshness proof binds each required physical artifact class to the current run/source identity, testing stale and wrong-run artifacts independently while companion artifacts remain valid.

Machine receipts cannot judge semantic test quality. A distinct reviewer receipt evaluates whether tests express the AC, reject unrelated exceptions, cover meaningful negative cases, and truly test freshness. The hostile review receipt includes full request/response JSONL paths, complete verdict body and findings in the MCP session log, review identity, source/plan/gate digests, OverallVerdict, and both numeric scores. The BDPv4 manifest requires AGREE and scores of at least 98 percent at its declared gates. A missing review or incomplete receipt blocks rather than being inferred from machine green.

Implement an IProcessGuard-style service boundary in McpServer, not just an MCP handler or Codex preflight. Audit and guard at least EfTodoService.UpdateCoreAsync (currently can write Done directly), TodoExecutionService.SetTestPlanAsync/RecordValidationResultAsync/ValidateTransition (currently allows TestReady on test definition and accepts textual pass), RequirementsDocumentService and RequirementsDatabaseDocumentService, RequirementsService indirect TODO updates, transaction-gated wrappers, MCP stdio/REST routes, and internal QuadBrain/voice callers. A governed TODO/requirements mutation consults the same binding, lease, and state. Creating a new TODO is a bootstrap action that atomically inherits the workspace binding or signed unmanaged classification; it cannot create an implicit bypass.

For each guarded operation: resolve live binding; validate actor/lease/epoch/plan/policy and expected revision; check declared operation class and predecessor evidence; acquire a workspace/slice serialization lock; recheck live state under the lock; apply the mutation and process event; increment state revision; return a receipt. Database-backed process state and TODO writes commit in one transaction. For file-backed requirements, stage the target file and operation event, use atomic replacement under the same workspace lock, and reconcile intent/commit receipts after a crash; an uncertain pending operation blocks subsequent advancement. Idempotency keys make retries safe. Test the direct underlying service methods as well as external routes. Direct database writes by an administrator are outside the stated API threat model.

At guarded boundaries, compare manifest-declared protected production paths and the slice baseline with available edit and runner receipts. An observed early edit blocks the BDPv4 slice and records the required remediation/restart. The host has no guaranteed interception of arbitrary unrelated file tools; an unobserved edit that is later reverted cannot be proven absent. State that limitation in test results and acceptance claims.

### D. Failure, security, performance, and rollout decisions

Failure handling: ordinary memory remains fail-soft. Critical policy, binding, lease, guarded mutation, phase transition, accepted completion, and done fail closed. Confirmed memory not-found is distinct from MCP outage. A verified cache is readable context only. A missing WebAuthn credential, unknown validator, policy digest mismatch, stale plan snapshot, runner outage, reviewer absence, or uncertain file-backed mutation leaves the relevant gate blocked with a recovery receipt. No timeout or fetch failure silently selects ExplicitlyUnmanaged.

Integrity and security: exact policy ID/version/source pinning and SHA-256 are mandatory. The BDPv4 GitHub fallback verifies raw source identity before applying the declared five-character transform and verifying normalized MCP bytes. WebAuthn passkey private material remains operator-held; an agent API key cannot enroll or approve. Trusted runner/reviewer credentials and approval credential trust roots are separate. Never store secrets in policy capsules, cache, plan snapshots, evidence, or logs. Do not use semantic recall or title matching as policy or plan identity. Local cache hashes detect corruption but do not authenticate against hostile replacement; direct filesystem and administrator database modifications are outside the initial prevention boundary.

Performance: measure three separate distributions in the canary: warm plugin-local heartbeat work, end-to-end guarded calls including MCP, and full-capsule rehydration including byte and token counts. Warm plugin-local p95 must remain under 250 ms. The first unchanged phase/epoch may emit full exact text once; subsequent healthy calls use the small heartbeat. Establish server and full-rehydration baselines before canary and set reviewed rollout thresholds from those measurements rather than pretending network latency is covered by the 250 ms local target.

Rollout: Off -> Shadow in a test workspace -> Enforce for a BDPv4 canary -> second process/version fixture -> wider adoption after full suites, traceability, independent hostile approval, and performance review. Shadow classifies each existing TODO by approved governed binding or signed explicit-unmanaged record. A TODO already Implementing cannot be grandfathered: verify historical predecessor receipts or restart/remediate a new generation. Rollback uses Freeze, retaining state and receipts while blocking new governed transitions; it never converts incomplete work to done. Migrate cache schema by versioning and invalidation, preserve legacy ordinary descriptor keys, and preserve old TODO outer statuses.

Review and acceptance: the operator reviews this entire plan, the MCP schema/API, signing/bootstrap trust boundary, service-level route coverage, cross-store recovery behavior, cache lifetime, and migration path before increment A. A successful feature makes conversational context expendable: active exact policy and process state can be reconstructed from MCP, and guarded work cannot advance or be accepted without the current approved process, applicable full plan snapshot, lease, and predecessor evidence. It does not weaken BDPv4's human-readable source or claim to control every free-form reply or arbitrary local edit.
